# Architecture

## Layers
- **Controllers** (`app/Http/Controllers/{Admin,User,Api/V1}`): thin. Validate (Form Requests), call an Action, return a view or resource.
- **Actions** (`app/Actions`): one business operation each, e.g. a single purchase or a single wallet credit.
- **Services** (`app/Services`): shared capabilities that Actions use (wallet ledger, provider engine, pricing, KYC, notifications).
- **Support** (`app/Support`): small helpers, value objects, enums.
- Web and the mobile API call the **same Actions**, so rules live in one place.

## Routing
- `routes/web.php`: web UI. `routes/api.php` mounts `routes/api/v1.php` under `/api/v1`. A future v2 gets its own file.

## Frontend
- Blade layouts in `resources/views/layouts`; areas `public`, `user`, `admin`; reusable parts in `components`.
- Tailwind tokens in `resources/css/theme.css` (navy, brand blue, white). Mobile-first. Alpine.js for small interactions.

## Runtime choices (cPanel compatible)
- Sessions, cache and queue use the database driver. No Redis dependency.
- Queue worker will run via cPanel cron (`queue:work --stop-when-empty`) at deployment time.

## Domain rules
1. Every normal business setting is managed from the Admin Dashboard, not cPanel or `.env`. `.env` holds only infrastructure and secrets.
2. Each plan has its own ordered provider routes (Phase 7): a primary (priority 1) and any number of fallbacks by priority, unique per plan, each with the provider's own plan code and an optional provider cost. Providers are independent of the catalog and list the services they support. `RouteResolver` only lists routes in order with eligible/skipped reasons; the Phase 10 purchase engine tries the runnable ones in that order and fails over only after a definite failure. Providers are created by an administrator; none are seeded.
3. Each plan has separate prices for API User, Affiliate, Subscriber and Vendor.
4. Payment gateways sit behind one interface so several can run side by side (see "Payment gateways" below). The Monnify and Aspfiy adapters are future steps of Phase 9, built only after each gateway's official documentation is verified and sandbox credentials exist.
5. NIN, BVN and Exam PIN are separate customer-facing services (Phase 11). Data and Smile Data are separate services; Smile Data is blocked (Phase 11 CP5).
6. Virtual account/KYC requirements are configurable (phone, BVN, NIN, provider-required documents). An ID card is never assumed.
7. Sensitive KYC data is encrypted at rest and visible only to permitted roles.
8. Referral commissions (Phase 12) are Level 1 only: the buyer's direct referrer is paid, on the qualifying services only, from the customer's charged amount, into the referrer's Main Wallet. Rates and caps are set by staff per service. A commission is never changed; one staff action can reverse or cancel it, once.

## Engineering conventions
- Money: integer minor units (kobo), never floats.
- Wallet and transactions (Phase 8): see "Wallet engine" below. Idempotency keys on every money operation, purchase and webhook.
- Customers (`users`, `User`, `web` guard, Sanctum tokens) and staff (`system_users`, `SystemUser`, `admin` guard) are separate account systems. The admin area has its own session cookie (path `/admin`) and session table, set by `UseAdminSession`. Customer routes use `auth:web`; admin routes use `auth:admin`.
- Customer tier is `users.user_type` (`App\Support\Enums\UserType`), changed only through `ChangeUserType` by staff with `customers.change-type`. Customers never hold roles.
- Staff access is spatie roles/permissions on the `admin` guard (`SystemRole`, `SystemPermission`; Super Admin via `Gate::before`). Add staff abilities as `SystemPermission` cases and map them in `SystemRole::permissions()`, then re-run the seeder.
- Authentication: custom session controllers (Breeze-style). Customers sign in through `AuthenticateUser` (web and API), staff through `AuthenticateSystemUser`; both use `LoginThrottle` with separate counters.
- Configurable: email verification (`NADABO_REQUIRE_EMAIL_VERIFICATION`), API token lifetime (`SANCTUM_TOKEN_EXPIRATION`).
- Audit logs for admin and money-moving actions (Phase 16).
- Never log secrets, tokens, BVN/NIN, Exam PIN or serial values, purchase results or card data.
- Provider credentials: encrypted at rest (Laravel encryption, `APP_KEY`; keep `APP_PREVIOUS_KEYS` when rotating the key), write-only in the admin, hidden from serialization, never flashed as old input, logged or shown (only a last-four hint for values of 8+ characters). Every set, replacement and clear is recorded without the value.

## Wallet engine (Phase 8)
- **Structure:** one wallet per customer per wallet type (`wallets`, unique customer + type). Phase 8 has only the `main` type; the same generic engine serves Subscribers, Vendors, Affiliates and API Users. Currency NGN, integer kobo, status active or frozen (frozen: credits allowed, debits blocked). No holds: available balance = current balance.
- **Three records per operation:** `transactions` (what the customer sees: TXN reference, type, direction, amount, status, idempotency key), `wallet_ledger_entries` (append-only money movement: WLE reference, direction, positive amount, `balance_after_kobo`, entry type, staff creator) and the cached `wallets.balance_kobo`. Purchases, provider attempts, payments and withdrawals get their own tables in later phases and link to a transaction.
- **Ledger invariants:** entries are never updated or deleted (model guards, no routes); corrections are compensating `reversal` entries (`reverses_entry_id` is unique, so an entry is reversed at most once); for every wallet, cached balance = sum(credits) − sum(debits) = latest `balance_after_kobo`, and every entry's `balance_after_kobo` equals the running total. `php artisan wallet:verify` checks this and only reports; it never repairs.
- **Cached balance:** written only by `App\Services\Wallet\WalletService`, in the same database transaction as the ledger entry and transaction row. The column is unsigned (a negative balance is impossible at database level) and capped at `WalletService::MAX_BALANCE_KOBO`.
- **Concurrency:** every operation runs in `DB::transaction(..., 3)` (deadlock retry) and locks the wallet row with `SELECT … FOR UPDATE` before reading the balance, so operations on one wallet happen one at a time; no overdraft is possible. Future multi-wallet operations (transfers, payouts) must lock wallets in ascending id order. Proven by the MariaDB concurrency suite (`php artisan test -c phpunit.concurrency.xml`, database `nadabo_concurrency_test`): parallel processes cannot double-spend or lose updates, and removing the lock makes those tests fail.
- **Idempotency:** each transaction may carry a key, unique per customer. A repeated key with the same wallet, type, direction and amount returns the original result (nothing posted again); a reused key with different parameters is refused. The unique index is the last safety net for parallel retries. Admin forms use a one-time token, and so does the customer Buy confirmation (it is the purchase idempotency key, Phase 10); the future mobile API will use a client `Idempotency-Key`, and webhooks the gateway reference.
- **Statuses:** transaction pending → successful | failed, successful → reversed; anything else is rejected. Ledger entries have no status. Phase 8 adjustments are successful immediately.
- **Pricing and providers:** the wallet never calculates prices. Purchases (Phase 10, see "Purchase engine" below): `PriceResolver` quote → purchase + wallet debit (idempotent) → runnable routes in priority order → provider attempts (route, provider code and cost snapshots) → success, or exactly one refund credit and status failed. Margin = selling price − cost of the successful attempt, recorded on the purchase.
- **Deferred:** gateway adapters (9, Steps 2–3), cashback and extra wallet types (not scheduled), withdrawals and holds (14), maker-checker approval and general audit/reports (16), customer wallet API (18), customer transfers (later). Purchases, provider attempts and purchase refunds were built in Phase 10; commissions were built in Phase 12.

## Payment gateways (Phase 9 Step 1)
- **Payment vs wallet transaction:** a `payments` row (PAY reference) is a request to fund a wallet through one gateway; it moves no money. Money moves only when the gateway confirms the payment server-side: `PaymentService` then calls `WalletService::credit()` (idempotency key `payment:{PAY reference}`, type `funding`), which writes one successful funding transaction and one `funding` ledger entry, and the payment becomes `successful` with `wallet_transaction_id` set, all in one database transaction. The payment never updates a wallet balance itself. Gateway fees are absorbed by Nadabo: the credit equals the requested and verified amount.
- **Statuses:** `pending` → `successful` | `failed` | `review`; `review` → `successful` (staff recheck with a verified exact amount) | `failed` (staff closes it, no credit); `failed` → `review` (the gateway confirms payment later); `successful` is final. No manual "mark paid", no refunds. History is append-only (`payment_status_changes`, with source: customer, webhook, return, reconcile, admin).
- **Contract and registry:** every adapter implements `App\Services\Payments\Contracts\PaymentGateway` (capabilities, credential keys per mode, allowed checkout and API hosts, initialize, verify, webhook authentication and parsing). Adapters are registered in code (`config('payments.drivers')`, empty in Step 1). Gateway records are created by admins (no seeded gateways); `GatewayRegistry` joins records and adapters and decides configuration status (driver installed, mode allowed, all required credentials for that mode). There is no automatic failover between gateways.
- **Verification:** a browser return or webhook never proves payment. Both only trigger `verifyAndFinalize()`, which asks the gateway (outside any database transaction, short timeouts), then locks the payment row and applies the answer once: paid with exact amount and NGN → credit; mismatch (amount, currency or gateway reference) → review; failed → failed; pending/unknown → stays pending. A refused credit (e.g. balance cap) rolls back to a savepoint and moves the payment to review, leaving no partial financial state.
- **Webhooks:** `POST /api/webhooks/payments/{gateway-code}` (stateless, no session or CSRF, throttled). Order: unknown gateway 404; body over 64 KB 413 unread; gateway not configured 503; adapter authentication fails 401; malformed 400; then the event is inserted with a unique (gateway, event key) and a redelivered event is answered 200 without reprocessing. Rejected events are stored without payload. Only an allow-listed, sanitized payload is kept (no headers, secrets or card/bank data), and it is cleared after 180 days by `payments:prune-webhooks` (the outcome row stays). Signature schemes come only from each gateway's verified documentation; none is invented.
- **Concurrency:** payment row lock (`SELECT … FOR UPDATE`) + wallet row lock (inside `WalletService`), unique payment reference, unique (gateway, event key), unique `payments.wallet_transaction_id`, the `payment:{reference}` wallet idempotency key, and database transactions. No database lock is held during an HTTP call. The MariaDB suite (`tests/Concurrency/PaymentConcurrencyTest.php`) races duplicate webhooks, returns, reconciliation and staff rechecks: always exactly one funding transaction and ledger entry, the exact balance and a clean `wallet:verify`; removing the payment row lock makes it fail.
- **Reconciliation:** `payments:reconcile` runs every five minutes from the scheduler (`withoutOverlapping`; no queue worker needed on cPanel). It rechecks pending payments older than 2 minutes in small batches (oldest check first). A payment is never failed just because the customer did not come back: it fails only after `payments.pending_expiry_minutes` (default 60) plus a 30-minute grace AND a gateway check that still finds it unpaid. A payment confirmed after it failed goes to review.
- **HTTP:** adapters call out only through `PaymentHttpClient`: https only, only to hosts the adapter declares for the mode (admins cannot enter URLs, so no SSRF), 5 s connect / 15 s total timeouts, retries only for read-only verification (network errors and 5xx), never for an initialization POST unless the adapter declares it idempotent. Failures are logged with host and path only and with Authorization headers, secrets, tokens and sensitive payment fields redacted.
- **Credentials and live safety:** gateway credentials are per mode (sandbox, live), encrypted, write-only, hidden from serialization, never flashed, logged or put in history (only a last-four hint). Gateways start inactive and in sandbox. Live calls happen only when `payments.live_enabled` is on, the gateway's mode is live and every live credential is set; otherwise the gateway is "not configured" and nothing is sent. There is never a fallback from live to sandbox; a payment is always verified in the mode it was created in. Checkout redirects go only to an https host the adapter declares.
- **Limits (Settings Store):** `payments.min_funding_kobo` (10,000), `payments.max_funding_kobo` (50,000,000, and never above `pricing.max_amount_kobo`), `payments.pending_expiry_minutes` (60), `payments.live_enabled` (false).
- **Permissions:** `payments.view`, `payments.manage` (recheck, close review), `payments.gateways` (records, status, mode, priority), `payments.credentials`; Super Admin only by default, grantable in Roles. Every action re-checks the permission server-side.
- **Not built / deferred:** Step 1 is complete and closed (`b150142541ae41c92420d88185101500407a7f88`). The Monnify adapter (Step 2) is BLOCKED pending verified access to Monnify's official documentation; the Aspfiy adapter (Step 3) is NOT STARTED. No gateway-specific endpoints, webhook signature rules, checkout hosts, status mappings or credentials exist in the code; each adapter declares them only from verified official documentation. "Payment points" are not defined and are deferred (no virtual/reserved accounts, POS/agent points or loyalty points). Automatic gateway failover, refunds, withdrawals and purchases are out of scope.

## Purchase engine (Phase 10 Step 1, complete and accepted)
- **CP1 (done):** `purchases`, `purchase_attempts`, `purchase_status_changes`; purchase statuses pending/successful/failed/review, attempt statuses started/succeeded/failed_definite/unknown; durable (customer, idempotency key) guard plus request fingerprint; `purchase` transaction type and `purchase_debit` / `purchase_refund` ledger types; permissions `purchases.view` / `purchases.manage`.
- **CP2 (done): provider adapter foundation.** `App\Services\Providers\Contracts\ProviderAdapter` (driver, label, supported service slugs, credential keys, API hosts, timeout, `purchaseIsIdempotent()`, `canQuery()`, `purchase()`, `query()`); results are normalized to `succeeded`, `failed_definite` or `unknown` (`ProviderResult`, messages length-limited with long numbers masked). Outcome rule: only a documented provider response may be definite; timeouts, connection errors, 5xx, malformed or undocumented responses and adapter errors are `unknown` (`ProviderCaller` enforces this and calls a purchase exactly once). `ProviderAdapterRegistry` reads adapters from `config('providers.drivers')` (empty in production) and answers whether a route is **executable**: Phase 7 `RouteResolver` eligible (unchanged) AND an installed adapter for the provider's driver AND the adapter supports the route's service. `ProviderHttpClient` (separate from the Phase 9 payment client): https to adapter-declared hosts only (the admin-entered provider base URL is never used), adapter timeout clamped to config, purchase calls never retried, status queries retried on network errors/5xx only when the adapter asks, logs with host and masked path only and credentials, tokens and customer data redacted. Test-only adapters live in `tests/Support/Providers`. No real provider adapter exists.
- **CP1 hardening (done; required before CP3):** model guards plus composite foreign keys enforce: (1) a failed purchase and (2) a successful purchase both require the recorded debit; the debit and refund must each be a successful `purchase` transaction of the charged amount on the purchase's own wallet (refund a credit, debit a debit, never the same transaction; wallet match also enforced by foreign key); (3) the delivering attempt belongs to the same purchase (foreign key) and has succeeded; (4) successful and failed purchases never change again (not even `updated_at`); (5) cost and margin are written only in the save that records success and must equal the delivering route's cost snapshot (fixed cost, or face value minus the percent discount rounded down as in `PriceResolver`) and charged amount minus that cost (both null when the route had no cost); (6) attempts with a definite outcome never change again, unknown attempts stay open for re-checks; (7) an attempt's route belongs to the purchase's plan and (8) its provider is the route's provider (both also foreign keys, via the attempt's copy of the purchase plan), attempts are created only for pending purchases with an exact route snapshot; (9) recipients are stored in canonical form by `App\Support\Phone\NigerianPhone` (11-digit local format; `+234` + 10 digits not starting with 0 converted; no network-prefix check) and the fingerprint is computed from the canonical number. Raw query-builder updates bypass model guards (as in Phases 8–9); the purchase engine must save through the models.
- **CP3 (done): purchase service** (`App\Services\Purchases\PurchaseService`). `create()`: phone normalized, fingerprint checked against an existing (customer, key) purchase (same details → that purchase, no new debit; different details → refused), price quote (`PriceResolver`, capped by `pricing.max_amount_kobo`), at least one executable route, then one database transaction that locks the wallet row first, inserts the pending purchase (the unique key stops a parallel duplicate before any debit) and debits through `WalletService` (key `purchase:{reference}`). Insufficient balance, a frozen wallet or any refusal leaves no purchase and no debit. `execute()` runs only after that commit: under the purchase row lock it creates one attempt at a time (never while another is started or unknown; each route once), calls the provider outside any transaction through `ProviderCaller`, and applies the result under the lock: succeeded → successful with cost and margin from the route snapshot; failed_definite → next executable route; unknown/timeout/error → stop, stays pending (next re-check after 2 minutes, `config/purchases.php`), never refunded or failed over. When every route tried failed definitely (or none is executable any more and nothing was sent), the purchase fails with exactly one refund through `WalletService` (key `purchase-refund:{reference}`) in the same transaction. Proven by MariaDB races (`tests/Concurrency/PurchaseConcurrencyTest.php`): parallel purchases on one wallet, one key resubmitted in parallel, one purchase executed from many processes, parallel all-failed refunds and unclear outcomes; removing the purchase row lock makes them fail.
- **CP4 (done): re-checking unclear purchases.** `purchases:reconcile` runs every five minutes (`withoutOverlapping`), in batches of 50, oldest due first (`next_check_at`, or `created_at` for a pending purchase never scheduled, after 2 minutes). For a purchase whose attempt is `unknown`, it queries the provider's documented status lookup (only when the adapter `canQuery()`; otherwise nothing is called) outside any lock, and applies the answer under the purchase row lock: succeeded → successful (cost and margin from the route snapshot); failed_definite → failed with exactly one refund through `WalletService`, never a failover to another route; unknown or no lookup → unchanged, next check at 2, 5, 15 and 60 minutes after the unclear attempt, then every 6 hours (`config/purchases.php`); after 24 hours without a definite outcome → `review`, which never refunds or fails over by itself and is still re-checked every 6 hours until a definite provider answer settles it. An attempt left `started` for over 10 minutes (interrupted call) becomes `unknown` and is re-checked, never retried. A pending purchase with nothing unclear (never started, or every attempt failed definitely) continues normal execution. Staff re-check (`RecheckPurchase`, `purchases.manage`, active staff, re-checked inside the action) runs the same logic and records the staff member; there is no manual "mark successful" or "force failed/refund". MariaDB races cover scheduler vs staff, duplicate runs, conflicting answers and unknown answers.
- **CP5 (done): admin Purchases module** (Operations → Purchases; `purchases.view`). List with filters (status, service, network, provider, date range) and search (reference, recipient in any accepted phone format, customer name or email), 25 per page, eager-loaded (no N+1). Detail page separates what the customer bought and was charged from internal data (cost, margin, provider attempts with our and the provider's references, outcomes, timings, re-check counts) and shows the debit/refund transactions and history; no credentials, tokens or raw provider payloads are stored or shown. Staff action: "Re-check with provider" only for pending/review purchases (`purchases.manage`, checked again inside `RecheckPurchase`); every staff re-check is recorded in the history, also when no definite outcome was found. There is no mark-successful, force-fail/refund, edit or delete route.
- **CP6 (done): customer Buy Data and Buy Airtime** (`/buy`, `/buy/{data|airtime}`, `/purchases`; signed-in customers, `verified.optional`). `PurchaseCatalog` offers a plan only when the service, product and plan are active, the customer's type has an active price, the amount is within the plan's limits and at least one executable route exists (eligible route + installed adapter supporting the service); with no adapter installed (production today) the pages say "Not available right now" and nothing can be bought. Flow: choose (network, plan or airtime amount, phone) → confirmation page with the `PriceResolver` quote (face value, discount, fee, amount to pay) and a one-time token → `PurchaseService::purchase`, which re-resolves the price on the server and refuses if it differs from the confirmed amount; client-sent customer ids, statuses and prices are ignored. The token is the purchase idempotency key: a double submit returns the same purchase (one debit, one provider call); the same token with different details is refused. Phones go through `NigerianPhone` and are stored canonical. Result and history pages show only the customer's own purchases (another reference is a 404) with reference, service, plan/amount, recipient, amount charged, status (Successful / Pending / Failed / Under review) and date — never provider, cost, margin or internal error details. Separate per-customer limits: 30 confirmations and 10 purchase submissions per minute.
- **CP7 (done): MariaDB race tests, docs and final checks** (tests and documentation only; no application change). Added to `tests/Concurrency/PurchaseConcurrencyTest.php` (new `purchase_worker.php` modes `submit`, `credit`, `reprice`, `freeze`): parallel double submit of one confirmed Buy form through the HTTP kernel → one purchase, one debit, one provider call; one token reused with different details in parallel → exactly one purchase, the rest refused without a debit; purchases, definite-failure refunds and wallet credits racing on one wallet → exact final balance, nothing left pending; a price change racing with confirmed submissions → every purchase charged exactly its confirmed amount, stale confirmations refused without a purchase row, debit or provider call; a wallet freeze racing with purchases → no debit after the freeze, blocked purchases leave no row and make no provider call. Every race ends with a consistent ledger chain and a clean `wallet:verify`. Phase 10 Step 1 is complete and accepted (`9fcfacd`).

## Provider readiness (Phase 10 Step 2)
- No real provider is connected and none has been chosen: real provider onboarding is a future decision. When a provider is chosen, its adapter is built only from that provider's verified official API documentation (nothing about any provider's endpoints, authentication, formats or statuses is assumed), it must pass the adapter contract kit and the production policy below, and an administrator enters its credentials in the admin area (encrypted, write-only; never in code or the repository). `config('providers.drivers')` stays empty in production.
- **CP1 (done, accepted at `36f3acb`): provider readiness and the adapter contract kit.** A plan route is **runnable** (the engine's "executable") only when: (1) Phase 7 `RouteResolver` calls it eligible (unchanged); (2) an adapter is installed for the provider's driver; (3) the adapter supports the route's service; (4) every credential the adapter needs (`credentialKeys()`) is set, in addition to the credentials an administrator declared as required for Phase 7; and (5) if a base URL is configured, it is https on a host the adapter declares, with no port or login (`ProviderHttpClient::allows()`, the same rule `send()` enforces). Customer availability (`PurchaseCatalog`) and the purchase engine use this one check (`ProviderAdapterRegistry::isExecutable()`), so a route that cannot run is skipped before any purchase, debit or provider call. `ProviderAdapterRegistry::providerReadiness()` and `routeReadiness()` return names and states only (never credential values) with every reason, Phase 7 reasons first. Admin (`providers.view`; routes page also `services.view`): the provider list marks "Adapter installed" / "No adapter"; the provider page has an Adapter readiness section (installed adapter, the services it supports, the credentials it needs as set / not set, whether the base URL host is allowed, whether a documented status check exists, and the problems) and marks each supported service the adapter does or does not support; a plan's routes page shows Runnable / Not runnable per route with every reason, and the routing preview shows the eligible order and the routes runnable now. Customer pages are unchanged and never show provider names, hosts, codes or readiness details.
- **Adapter contract kit** (`tests/Support/Providers/AdapterContract.php`, test-only): definition rules (driver, label, service slugs, credential keys, bare https host names, timeout within the configured range) and behaviour rules for HTTP adapters, run through `ProviderCaller` with every request faked: 5xx, non-JSON, empty and undocumented answers and network failures must come out `unknown`, requests go only to declared https hosts, a purchase request is never sent twice, and no credential value or recipient number reaches results or logs. The **production policy** (`productionViolations()`, enforced by a test on `config/providers.php`): a registered adapter must pass both, use a driver an administrator can enter on the provider form, have a documented status check (`canQuery()`) so unclear outcomes can be settled with the provider, and never be a test-only adapter. The kit is itself tested against a probe adapter broken one rule at a time. Every real adapter must pass the kit in addition to tests built from its provider's documentation.

No real provider is connected (`config('providers.drivers')` is empty), so in production nothing can be bought until a provider is onboarded; the test-only FakeProvider exists only in the test suite. Operational guarantees, each covered by feature tests and, where concurrency matters, by the MariaDB suite:
- **One money path.** Money moves only through `WalletService` (wallet row lock, ledger entry and cached balance in one database transaction). Purchases are created, debited, settled and refunded only by `PurchaseService`; no route edits, deletes, settles or refunds a purchase by hand.
- **Server-side price and ownership.** The price is always resolved on the server by `PriceResolver`; a confirmed amount that no longer matches is refused. Client-sent prices, customer ids and statuses are ignored, and customers see and open only their own purchases (another reference is a 404).
- **Exactly once.** One confirmation token gives one purchase and one debit, also under parallel double submits, and a repeated submission never triggers another provider call; each route is tried at most once per purchase. The same token with different details is refused. A purchase is refunded at most once, and only when nothing can still deliver it: every route tried failed definitely, or nothing was sent and no route is runnable any more.
- **Unclear outcomes are never guessed.** A timeout, network error, 5xx, malformed or undocumented answer is `unknown`: the purchase stays pending, is never refunded or failed over, and is re-checked with the provider's documented status lookup at 2, 5, 15 and 60 minutes, then every 6 hours. After 24 hours it moves to review, which only a definite provider answer settles. Failover to the next route happens only after a definite failure.
- **Only runnable routes are used.** A route is used only when it is runnable (Phase 7 eligible, adapter installed and supporting the service, credentials set, base URL host allowed); otherwise the purchase is refused before any debit. Provider calls happen after the debit commits and outside database transactions, go only to adapter-declared https hosts, and a purchase call is never retried.
- **Watching and checking.** The admin Purchases page and dashboard show pending, review, overdue checks (due for more than 15 minutes means the scheduler is not running or is behind) and today's results; Today's Sales uses the business day. `purchases:verify` and `wallet:verify` run daily, only report (never repair), log an error when they find a problem, and are safe to run at any time.
- **Maintenance mode.** It blocks only new purchases (after the duplicate-submission lookup, before any pricing, debit or provider call); purchases in progress, re-checks, refunds, the admin area and wallet funding continue.
- **No secrets or internals leak.** Provider credentials are encrypted and write-only. Logs, provider results and admin readiness views never contain credential values or raw provider payloads, and customer pages never show provider names, costs, margins or internal errors.
- **Proven under concurrency.** The MariaDB suite (`php artisan test -c phpunit.concurrency.xml`, 24 tests) shows no overdraft, no double debit, refund or provider call, exact balances and clean `wallet:verify` / `purchases:verify` while purchases, refunds, credits, re-checks, price changes and wallet freezes race.

Running it in production: a cron entry for `php artisan schedule:run` every minute (purchase re-checks and payment reconciliation every five minutes, daily integrity checks and token pruning); no queue worker is needed for purchases. Before deploying, confirm the stored `app.maintenance_mode` is off, then run `php artisan migrate` and `php artisan db:seed --class=SettingsSeeder`. Before anything can be sold, a provider must be onboarded and prices entered for each plan and customer type.

  - Level 1 only: the buyer's direct referrer is paid; the engine reads one referral link.

A failure to read the referral link is logged only, because there is no referrer to record. A database abort (deadlock, lock wait timeout, lost connection) is passed on, so the whole success is retried or settled later by the purchase re-checks. The commission step itself retries nothing.

The models refuse each one ("A KYC submission takes no new … once it has a decision."), and the triggers refuse the same inserts written as raw SQL. On MariaDB and MySQL the triggers lock the submission row (`FOR UPDATE`) and read the reviews with a locking read (`LOCK IN SHARE MODE`). The decision holds a shared lock on the submission until it commits, so an insert that races a decision waits for it and is then refused. SQLite serialises writers, so a plain check is enough.
- **Trigger limits:** `TRUNCATE` and `DROP TABLE` do not fire row triggers. The open-slot table has no update or delete trigger. The database itself guarantees one slot per customer (the table's primary key), no slot for a decided submission (`kyc_open_submissions_no_insert_after_decision`), and that a decision frees its slot in the same statement as its review (`kyc_reviews_release_open_slot`). It does not refuse a delete or update of an undecided slot by an account that holds that privilege. That protection depends on privileges: the application account should hold no `DELETE` or `UPDATE` on the slot table (see Production database privileges), and the migration account needs `DELETE` only because the release trigger runs with its privileges. `TRUNCATE`, `DROP`, `ALTER` and `TRIGGER` on KYC tables are privilege-dependent as well. If the release trigger is absent, a review written directly (raw SQL, or the review model, which has no check of its own) still commits and leaves its customer's slot in place. - **Free-text reasons:** a decision's reason is trimmed, and a reason that holds eleven digits in a row, such as a BVN, NIN or phone number, is refused before anything is written, whatever the decision. Trimming is PHP's `trim()` with its default characters (space, tab, line feed, carriage return, NUL and vertical tab) at both ends; a no-break space at an end is kept, and a blank approval reason is stored as no reason, as the ledger stores it. - **Key rotation (before changing `APP_KEY`):** identity values are sealed with the app key, and their duplicate checks (`lookup_hash`) and phone fingerprints are keyed from every key the app holds: the current `APP_KEY` first, then each key in `APP_PREVIOUS_KEYS` (comma-separated). Steps: (1) put the current `APP_KEY` at the front of `APP_PREVIOUS_KEYS`, keeping the entries already there; (2) set the new `APP_KEY`; (3) rebuild the config cache if the host caches it (`php artisan config:cache`); (4) confirm that one existing identity value still decrypts, without printing it. Never remove a key while any KYC or Phase 11 row was written under it: no inventory of rows per key exists, so treat every key the app has used as permanent. No re-encryption command exists. - **Identity values in output and traces:** the model hides `ciphertext` and `lookup_hash` from arrays and JSON, its debug output shows only the mask, and `serialize()`, `var_export()`, `var_dump()` and `print_r()` of a stored value contain no plaintext (tested). - **Migrations on MariaDB are not atomic:** MariaDB applies DDL (`CREATE TABLE`, `CREATE TRIGGER`, `DROP TRIGGER`) without a transaction, and Laravel records a migration only after it completes, so a KYC migration that fails part way leaves its finished objects behind. The trigger migration runs again safely: it drops each trigger before creating it. The table migrations do not, so recover them by hand: (1) list what exists (`SHOW TABLES LIKE 'kyc%'` and `SELECT trigger_name FROM information_schema.triggers WHERE trigger_schema = DATABASE() AND trigger_name LIKE 'kyc%'`); (2) confirm that each leftover table of the failed migration is empty (`SELECT COUNT(*)`); (3) drop only those empty leftover tables and triggers of the failed migration, never a KYC table that holds a row; (4) run `php artisan migrate` again. If a leftover holds a row, stop and report it. Do not edit the `migrations` table by hand. Rollback is not atomic either: a failed rollback can leave some triggers dropped, and running `php artisan migrate` restores them.
- **Rollback and seeded requirements:** `DatabaseSeeder` seeds the four KYC requirements on every fresh install (`KycRequirementsSeeder`), so `kyc_requirements` holds rows from the first seed.
